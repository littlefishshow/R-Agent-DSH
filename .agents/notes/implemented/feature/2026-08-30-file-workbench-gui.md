# Agent Note: File-workbench GUI (document editing with selection sub-sessions)

Status: implemented

English | [中文](2026-08-30-file-workbench-gui.zh.md)

## Problem

The Web GUI projects a Workspace only as its conversations; it cannot switch the same Workspace to a complete filesystem tree, read and edit Markdown, or act on a selected passage without hand-copying it into chat. The required UI follows the R-Agent Cockpit model: a left Chat / Files mode switch, the original conversation surface in Chat mode, a VSCode-like file reader replacing the center in Files mode, focused selection conversations, highlights that persist while those windows are minimized, and accepting a rewrite straight back into the file. The capability ships **as installable plugins**, while reusing dsh's session, compaction, session-log, and trajectory machinery instead of building a parallel agent runtime.

## Decision

Three opt-in plugin packages plus one installable bundle, layered over the shipped Web composition; the base UI keeps its default behavior and presentation when the bundle is absent.

- **`packages/host/fileworkbench-io`** (host) mounts one generic [Connection RPC channel](../../../../packages/client/connection/README.md) `/rpc-fileworkbench` with file IO plus `startSelectionSession` and `deleteSelectionSession`, without touching the shared apiproxy `RpcMethodMap`. File endpoints use absolute Node filesystem paths rather than sandbox-confined `ctx.fs`; selection endpoints additionally require the named Workspace to own the path. The Host owns one stable parent Agent/Session per Workspace-and-file pair. `readText` caches the exact document snapshot already returned to the browser. A selection start checks only current file metadata against that cached version, so it never rereads the Markdown body. The stable parent appears in the conversation tree as `[File] <workspace-relative path>` and records the first cached `<file_context>` in an Agent-driven model-free turn, keeping the Agent's turn counter synchronized before later human prompts. If another Host path already keeps that root live, File Workbench reuses the live Agent without claiming its teardown handle or asking persistence to prepare the same Session again. Every selected passage creates an ordinary child with `parentSession` pointing at that root, no inherited events, and exactly one child-local `<file_context>` before its selection instruction. The hidden instruction source carries the browser selection metadata, and a `fileWorkbenchSelection` Session projection exposes it for reload restoration without adding a parallel store or another model-visible message. The pre-step listener rejects a missing or repeated child file context. Unchanged files give the parent and sibling children byte-identical context messages; zero event inheritance keeps each child request at one file context, and changed files affect only later children. The operator's first explicit question or modification request becomes the child title. Closing or accepting a created child stops its Agent, detaches it from the Workspace, and calls the common `SessionPersistence.delete()` operation. The channel remains loopback-only by default because arbitrary file access is as sensitive as shell access.
- **`packages/client/ui-layout-workbench`** (web) keeps the base three-column geometry but **replaces** `ui-layout` to add a mode-swapped center. The original `sidebar` remains mounted in both modes. Chat renders `conversation`; Files renders `workbench`; both center subtrees stay mounted so switching modes preserves the conversation. It re-provides `ctx.layout` unchanged and provides the shared, persisted `ctx.workbenchLayout` mode.
- **`packages/client/ui-file-workspace`** (web) contributes the animated Chat / Files segmented switch, overlays the original sidebar Workspace region with a filesystem projection only in Files mode, occupies the `workbench` center reader, and contributes selection windows through `shell.overlay`. The filesystem roots come directly from `ctx.workspaces.list.items`; adding uses the Host native picker followed by `ctx.workspaces.create()`, and removing calls `ctx.workspaces.delete()` without deleting the directory. Roots expand into every direct directory and regular file, with children loaded lazily. The header title, add action, list inset, row height, typography, folder state, selection tint, and shared Menu component match the base conversation Workspace browser, while new, delete, copy, paste, and rename operations target the real filesystem. The reader uses the conversation's 748px content width and filename-only tabs. Markdown retains rich rendering, relative local images, editing, and selection actions; common UTF-8 source/config files use a monospace reader/editor; supported raster images use fitted previews; PDF and other binary types show an explicit unsupported-preview panel. Markdown selection records exact readable-text offsets and combines CSS Custom Highlight paint with same-position DOM hit targets carrying the highlight id. The readable-text projection replaces each KaTeX subtree with its TeX annotation once and wraps it as Markdown before sending it to a child or rendering the scrollable selected-text card. Ask and modify open a draft window and send nothing until the operator supplies a concrete instruction; explain and summarize start immediately. The compact window hides the durable file-context and branch-opening messages, uses the operator's first instruction as its title, and continues to show later follow-ups. Its composer treats composition Enter as IME candidate confirmation rather than send, including Safari's composition-end delay and legacy key-code signaling. Its Chat tab renders only Assistant text blocks; reasoning remains in the native Trajectory tab. A modify answer is accepted when it contains exactly one `markdown` or `md` fenced block and the captured source range still matches byte-for-byte; surrounding prose is ignored rather than written. Each child drives a streamed conversation and `ui-trajectory`'s complete trajectory renderer in a movable, resizable window portaled to the document body. Watching a child calls `SessionRuntime.ensureOpen()` before relying on its snapshot, so history and live replies update inside Files mode without changing the current main conversation. On reload, the client scans `fileWorkbenchSelection` values on live Session summaries, reopens referenced documents only after Files mode is selected, and reconstructs each child as a minimized window with its clickable highlight. Plugin startup removes historical File Workbench roots and children from the Workspace archive set, restoring the root/child tree without changing ordinary archived sessions. Closing removes the highlight after Host Session deletion succeeds; accepting a modification writes the window's source tab even if another tab is active, removes the highlight after the file write, then leaves a cleanup-only window if Session deletion needs retry. The base sidebar emits a pre-start event so this plugin selects Chat before the unchanged New Session action runs.
- **`packages/bundle/file-workbench`** (`@deepseek-ai/dsh-file-workbench`) is the installable unit: a `dsh.bundle` whose `cordis.patch.yml` disables base `ui-layout` and inserts the three feature rows. It **depends on** those packages plus compatible `client-runtime`, `ui-sidebar`, `ui-workspace`, `ui-trajectory`, and `ui-primitives` versions carrying the background Session API and client contracts it extends, so `dsh plugin add` links the complete feature into the profile where the browser-roster scanner resolves it by name. Install with `dsh plugin --profile web add @deepseek-ai/dsh-file-workbench`.

The Host retains every selection-child `AgentHandle` and every file-parent handle it creates or resumes. A file parent already opened through another Host path remains owned by that path and is reused only as a live Agent. Stable file ids survive browser reloads and resume after Host restart. Parent and child both use the current default model and the same agent preset generation; a child keeps durable `parentSession` but starts with no inherited events. The parent supplies tree identity and preset composition, while the child owns its one file-context message and independent conversation. The browser filters the two hidden opening messages from the compact floating view. The complete child log remains available to compaction, persistence, reload, the Workspace tree, and the native conversation and trajectory views. The file-workbench extension retains ordinary fork-lineage presentation, so both grouped and flat conversation lists render each selection child beneath its stable file parent.

The file snapshot and selection instruction remain separate durable child messages. The child appends one plugin-sourced file context and one model-side user-role instruction, neither of which enters the compact floating transcript. The file-workbench `agent/pre-step` listener calls `next()`, requires exactly one file context in the first child step and none later, and stably partitions the final claimed batch into runtime context, file snapshot, then selection input. The model request sees the agent preset's system prompt, current-step runtime context, one file context, then the selection instruction. Sibling selections over one unchanged document receive byte-identical context messages at the same request position while their questions stay on separate child Sessions.

The minimized dock uses a minus action that hides only its compact entry. The child Session, projection, and source highlight remain live, and clicking that highlight restores the window; permanent deletion remains a window-header action.

Earlier File Workbench builds could append a model-free activation turn outside the Agent driver, then reuse that turn number for the first human prompt. The browser Session projection removes an earlier same-number turn's boundaries only when it contains context but no human, assistant, step, or tool activity. The raw log and model history remain unchanged, and every duplicate turn containing conversation work still fails closed.

## Alternatives considered

**Add `host.readFile`/`host.writeFile` to the shared apiproxy `RpcMethodMap`.** Rejected: it widens a contract every client and the wire schema share for one feature's file IO. The generic `ctx.connection.rpc` channel already carries a trust fence and lets the plugin own its endpoints, keeping the shared surface unchanged.

**Fork the whole web-app bundle and edit a copied UI (the literal "back up the UI" reading).** Rejected: dsh composes UI from independent slot plugins, so a physical copy diverges from the base and cannot track it. Additive plugins plus a bundle overlay keep the base runtime untouched and the feature opt-in.

**Distribute the feature by editing `dsh-web-app`'s dependencies, or by shipping an `examples/*/cordis.yml` `--patch` overlay.** Rejected: editing the base bundle couples the shipped default to an opt-in feature, and an example overlay is a dev quick-start, not a distributable unit — its `--patch` path references packages by name that a foreign harness has no reason to have installed. The installable `dsh.bundle` per [docs/user/develop/basic/publish.md](../../../../docs/user/develop/basic/publish.md) is the sanctioned mechanism: it carries its own dependencies, so `dsh plugin add` links them into the target profile's flat (`nodeLinker: hoisted`) `node_modules` where the browser-roster scanner resolves them. A local `link:`-from-source install nests the bundle's `workspace:` dependencies and the scanner misses them; a published or `pnpm pack`ed install rewrites those ranges to real versions and resolves them through the profile's hoisted layout.

**A separate selection-context tree beside Session storage.** Rejected: it would duplicate the event log, compaction state, lineage, replay, deletion, and trajectory ownership, then require synchronization after reload. Native Session lineage supplies the requested tree: each file owns one parent Session and every selected passage becomes its durable child, while the floating window is only a filtered projection.

**An always-visible fourth column.** Rejected after user review: it separates the file and conversation workspaces into simultaneous blocks, while the requested model is mutually exclusive Chat / Files modes. The layout fork now keeps the base three columns and swaps the center content while preserving the hidden conversation subtree.

**A second persisted file-folder registry.** Rejected after user review: it gives one directory two unrelated identities and makes adding a file root depend on the optional browse capability. The Workspace registry is the single authority; Chat projects sessions and Files projects directory contents from each `WorkspaceView.path`. The Host native picker remains the only add interaction.

**Highlights by rewriting MarkdownText's DOM.** Rejected: wrapping rendered nodes fights the streaming Markdown renderer. The CSS Custom Highlight API paints ranges over live text without structural edits; engines without it fall back to the dock/chip affordance.

## Consequences

The base Web UI is unchanged unless the bundle is installed into a profile; the feature is a true opt-in layer. Chat retains the complete original conversation functionality and remains mounted while Files is active. Both modes share Workspace identity, ordering, addition, and removal; switching changes only whether the sidebar projects sessions or filesystem contents. `ui-workspace` provides a default-off, reference-counted presentation control; this plugin retains it so file parents and selection children appear as lineage only for the plugin's lifetime. File operations use arbitrary absolute host paths, intentionally give up `ctx.fs` confinement, and are therefore loopback-only by default. Every selection sub-window is an ordinary dsh Session, so compaction, durable history, lineage, deletion, and trajectory require no new context store. `ui-trajectory` lets plugin windows render the same complete trajectory implementation as the main tab. Costs: `ui-layout-workbench` duplicates the base frame's drag-handle and concession structure; each active file parent contributes complete file content to its children; highlight paint needs the CSS Custom Highlight API. Pure logic, shared-Workspace projection, mode handoff, child-session lifecycle, permanent deletion, window controls, Markdown image authorization, context ordering, and absolute-path filesystem operations have focused coverage.
